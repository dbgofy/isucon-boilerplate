# 未ブロック Issue の実行

## ゴール

次のいずれかに到達するまで進める。

- 取得した Issue の完了条件を満たし、後続タスクがその成果を利用して進められることを確認して、その Issue を close した。
- 対象範囲を再確認した結果、取得可能な Issue がない。

一度に取得する Issue は 1 件とする。PR 作成や実装完了だけをゴールにしない。外部の判断や権限が必要で続行できない場合は、未達であることと再開条件を報告し、完了扱いにしない。

## 1. 対象と運用を確認する

1. ユーザーの指定、作業ディレクトリ、Git remote から対象リポジトリと範囲を特定する。特定できない場合だけユーザーに確認する。
2. 対象の `AGENTS.md`、Issue / Project / Milestone の運用、既存のスキルを読む。必要な実装、テスト、PR、マージ、デプロイ、成果物の保管ルールを把握する。
3. 認証中の GitHub アカウントを取得する。「自分」はこのアカウントを指す。ユーザー名を推測しない。
4. GitHub コネクタを優先し、不足する操作は認証済みの `gh` / API で補う。実際に利用できる権限とツールを確認する。更新に必要な機能がない場合は成功したと扱わない。

## 2. 候補と依存関係を調べる

認証済み `gh` と `jq` が使える場合、`.agents/skills/run-ready-issue/scripts/list-issues.sh OWNER/REPO` で未完了 Issue の調査用 JSON を一括取得する。引数省略時は現在のリポジトリを使用する。`truncated` に列挙された項目は個別に最後まで取得する。`graphqlPages` は Issue 一覧取得に使った GraphQL ページ数であり、明示したリポジトリに対する通常時の API 呼び出し数に相当する（再試行や後続の個別取得は含まない）。この出力は選定結果ではなく、関連 PR、子 Issue、blocking、前段 Milestone や依存先の成果など含まれない情報は別途確認する。取得失敗時は候補なしと判断しない。

未完了 Issue をページネーションの最後まで確認する。検索上限に達した場合は Milestone などで分割して調べ、未取得の範囲を「候補なし」と判断しない。PR は候補から除外する。

候補ごとに本文、コメント、完了条件、assignee、Project の Status、Milestone、親子関係、GitHub の Issue dependencies（blocked by / blocking）、関連 PR を読む。本文やコメントにのみ書かれた前提条件も確認する。依存先は別リポジトリも含めて現在の状態と成果を確認する。

Todo は未着手を示し、停止理由ではない。`needs-user-action` label や不足情報だけで候補から除外しない。資料確認、実施済み事項の照合、不足情報の具体化、ユーザーへの確認がその Issue の作業として可能なら取得対象にする。実機操作や外部変更に不足情報・承認が必要でも、その操作だけを保留して独立作業は進める。

次のものは取得しない。

- 未解消の blocked by、未完了の前提作業があり、当該 Issue の調査・確認を含めて着手できない。
- In Review の人間対応や Waiting の処理・依存先待ちが解消していない。解除済みの自分の作業は再開を優先し、Status の表示だけで解除済みと判断しない。
- 他の担当者が進行中、または同じ目的の PR / 作業が進行中である。既存の自分の作業がある場合は重複作成せず再開を優先する。
- 目的・完了条件が不明で、調査やユーザー確認の具体化すら進められない。
- 次節の前段マイルストーンの条件を満たさない。

ラベルが付いていないことだけで未ブロックと判断しない。親子関係を依存関係と取り違えない。状態を取得できない場合は未確認として保留する。

## 3. 前段マイルストーンを確認する

1. リポジトリで明記された順序やフェーズ番号から候補の前段マイルストーンを特定し、それ以前に未完了の段階が残っていないか確認する。作成日時や番号だけから順序を推測しない。不明なら確認が取れるまで当該候補を保留する。
2. 前段が未完了なら、その後のマイルストーンの Issue には着手しない。取得可能なら前段側の Issue を候補として調べる。
3. 前段が open だが作業は完了している場合、全 Issue の状態と成果・完了条件を確認し、マイルストーンの URL と根拠を添えて、ユーザーにそのマイルストーンを close するよう促す。マイルストーンを勝手に close しない。ユーザーが close し、最新状態で確認できるまでは後段を保留する。
4. 前段が closed でも未完了の前提 Issue や成果不足があれば着手しない。closed の表示だけで実作業の完了を推定しない。
5. 最初のマイルストーンは前段チェック不要。マイルストーン未設定の Issue は、明示された前段条件と個別依存関係を確認し、運用上の紐付けが不明なら保留する。

## 4. 取得を確定して状態を変える

ユーザー指定の優先順位、既存の優先度、前段の順、後続を解放する効果を見て候補を 1 件選ぶ。同等なら小さい Issue 番号を優先する。選定理由と完了条件を短く伝える。

変更直前に Issue、依存先、前段マイルストーン、assignee、Status、関連 PR を再取得する。競合や着手自体を妨げる新しい依存関係があれば取得せず選び直す。人間への確認を含む作業が可能な場合は、不足情報だけを理由に取得を取り消さない。

1. 選んだ Issue を認証中の自分にアサインする。他の assignee を無断で外さない。
2. 対象 Project の既存の Status を `In Progress` または運用で定義された着手中の値へ更新する。Project・field・option の実際の ID / 値を調べ、ラベルや Issue の open 状態で代用しない。Project が複数ある場合は運用対象を確認する。
3. 再取得して assignee と Status の両方が反映されたことを確認してから実作業を始める。失敗したら修復し、修復できなければ不足する権限や設定を報告する。Project が存在しない場合も変更できたと装わない。
4. 既存運用に従い、目的、根拠、前提条件、実行手順、検証方法を Issue に記録する。

## 5. 実行して完了条件を検証する

対象の運用に従って作業する。既存ブランチや worktree、PR があれば再利用し、実装、必要なテスト、レビュー、反映、成果物の保存まで完了条件に必要な範囲を進める。新たな承認が不要な範囲は確認待ちにせず進める。必要な承認や権限を迂回しない。

未着手の Issue は label・依存関係だけで In Review / Waiting に変更せず Todo のままにする。取得時点で分かっていた不足情報も、着手後の確認で必要な対応と待機理由を具体化する。独立して進められる作業を終え、実際に人間の回答・操作や処理完了を待つ段階になったら Issue に事実、試したこと、残作業、待っている対象、解除条件、再開手順を記録する。人間の確認・レビュー・判断・入力・操作待ちは `In Review`、ベンチマーク・非同期ジョブ・依存 Issue 等の完了待ちは `Waiting` に更新して再取得確認する。人間の対応が必要なら In Review を優先し、`needs-user-action` label も付ける。処理待ちだけではこの label を付けない。待機中は Todo や Done で代用せず、解除を確認して実作業を再開するときに In Progress へ戻し、不要になった label を外す。未完了の Issue を close せず、別の Issue を抱えて放置しない。

完了判定では次をすべて確認する。

- 完了条件を項目ごとに実測、テスト結果、成果物、関連 PR などの証拠と対応付けた。
- 成果が必要な場所で利用できる。マージやデプロイが必要なら完了済みで、ローカル変更や未マージ PR だけで完了扱いにしていない。
- 当該 Issue に依存する後続 Issue を一覧し、それぞれが必要とするコード、設定、文書、権限、成果物などを利用できることを確認した。
- 後続の開始手順や引き継ぎ情報が揃い、当該 Issue に由来するブロッカーが残っていない。後続に別の未完了依存先がある場合はそれを明記する。当該 Issue の責務が完了していれば、他の依存先まで実行する必要はない。
- 後続がない場合も、依存関係を調べて存在しないと確認した。

証拠が不足する場合は検証を続ける。PR を作ったことだけで close しない。

## 6. close と終了確認

1. close 直前に Issue の最新本文・コメントと依存関係を読み、追加された条件や再発がないか確認する。
2. Issue に完了条件ごとの結果、検証の証拠、成果物、関連 PR、後続の着手可否と残る別依存を記録する。
3. Issue を completed として close し、Project の Status を `Done` または既存の完了値にする。PR による自動 close が起きていれば重複せず、close の根拠を検証する。
4. 再取得し、Issue が closed / completed、Project が完了状態であることと、後続から見た依存状態を確認する。自動連動を仮定せず、失敗した更新は修復する。
5. close できた Issue、結果と検証、後続の状態を報告して終了する。次の Issue の取得を自動で始めない。

取得できる候補がない場合は再取得して変化がないことを確かめ、調べた範囲、除外理由、未完了の前段、close を促すマイルストーン、再開条件を報告して終了する。人間への質問だけをチャットに出して Todo のまま終了しない。取得・着手した Issue は担当・Status・待機理由・解除条件を Issue に記録し、In Review / Waiting の反映を確認する。取得後に外部待ちで止まった場合は「取得可能 Issue なし」と混同せず、取得した Issue の未完了状態を明記する。
