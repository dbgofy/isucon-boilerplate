# 目的

スコア計算、失敗条件、初期化の扱いをチームで共有し、以後の計測と比較の前提にする。

# 前提条件

- `read-regulation.md` と `read-manual.md` が完了している。
- 問題固有のエンドポイント名や解答手順を、未確認のまま確定事項にしない。

# 対象サーバー

なし。

# 作業

- マニュアルとレギュレーションから、計測時間、スコア、減点、失格条件を抜き出す。
- initialize の有無と、計測前に必要な状態を確認する。
- ベンチマーク実行方法と、結果の確認場所を記録する。
- 不明点は推測と確認済みの事実を分けて Issue に書く。

## 実行例

コマンドは実行例である。問題や環境によって構成、パス、サービス名、接続方法は異なる。Issue に記録したユーザー提供情報と実機の状態に合わせて読み替える。

## 1. マニュアルから計測条件を抜き出す

```bash
gh issue comment "$ISSUE" --body "$(cat <<'EOF'
## 確認済みの事実

- 計測時間:
- スコア計算:
- 減点 / 失敗条件:
- 失格条件:
- initialize の有無と、計測前に必要な状態:
- ベンチマークの実行方法:
- 結果の確認場所（ポータル / ログ）:

## 不明点（推測と分けて書く）

- 内容:
- 確認担当:
EOF
)"
```

## 2. 実行方法だけを手元で再現可能にする

ポータル操作が本体なら、画面の手順を箇条書きする。CLI がある場合は確認したコマンドを書く。

```bash
# マニュアルに記載がある場合のみ。未確認のバイナリを実行しない。
# ./bench run --target https://...
```

# 確認方法

```bash
gh issue view "$ISSUE"
```

成功 / 失敗の判定基準が、事実と不明点に分かれて読めること。

# 失敗時の復旧

- 記載が見つからない: 空欄のまま「未確認」と書き、運営またはマニュアル再読の担当を決める。
- メンバーで解釈が割れた: 引用箇所を Issue に残し、推測側に寄せない。

# 完了条件

- 成功・失敗の判定基準をチーム内で参照できる。
- 問題固有のエンドポイント名や解答手順を、未確認のまま確定事項として書いていない。
